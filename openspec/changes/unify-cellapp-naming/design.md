# Design

## Context

动机见 proposal.md。主仓库和子仓库均有先前未提交工作；客户端已完成品牌迁移，旧命令与状态受兼容规格保护。运行中的本地 PostgreSQL 使用旧角色/库名；更改 Compose 初始化变量不会修改已有卷。

## Goals / Non-Goals

统一当前用户界面、构建产物和开发说明；保护旧开发账号、客户端配置、历史事实及本地工作。不操作已有数据库角色/库名或云资源，不更改客户端协议，不发布 npm 包，不改变主仓库固定客户端版本。

## Decisions

品牌拼写按用户后续确认统一为 Cellapp/cellapp，规则见 docs/standards/brand.md；公开客户端在自己的 AGENTS 内保留相同规则。品牌文案与测试期望同步，不改变命令和协议。

1. 默认新库/角色改为 cellapp。文档提供旧连接串继续使用与停机备份后原位改名步骤；不通过删除卷重新初始化。
2. 开发登录在事务内取专用 advisory lock，检查旧/新 issuer 是否冲突；存在旧账号且没有新账号时将 issuer 原位改名，保留 id 和关联资源；随后沿用正常登录。双账号存在则失败并交由人工处理，不能自动合并所有权。
3. Go module/import、根 npm name/锁文件、服务二进制、图表 JSON/HTML 配套改名。图表授权与构建节点调整为实际顺序，逐文件上传替代不准确的流式表述。
4. 历史验收事实不改写，历史文档重跑命令使用新配置。仅兼容、身份迁移测试、升级说明与历史记录可出现旧名。
5. 不改数据库结构，不新增迁移；本轮只更新身份数据。已有初始迁移执行器的版本跟踪改进不在命名修正范围。

## Risks / Trade-offs

- 已有卷无法使用新默认连接串 → 保留旧 DATABASE_URL 或按照运维步骤停机原位改名；不执行用户现有数据库升级。
- 开发身份重复或并发登录 → 事务锁、冲突拒绝、旧 owner/凭证/应用保留及并发回归验证。
- 共享文件存在先前修改 → 使用修改前快照核对本轮差异；不批量暂存或提交混合工作。

## Migration Plan

新安装直接使用 cellapp 数据库和构建产物。已有环境备份后选择旧连接串或原位改名；开发登录自动更新旧身份。回滚使用备份和旧配置，身份 issuer 需按相同账号 ID 改回；不能同时运行旧新 dev 登录服务。验证包括类型、构建、Go vet、客户端回归、隔离 PostgreSQL race 与真实 Chrome；本轮不重复云端存储验收。
