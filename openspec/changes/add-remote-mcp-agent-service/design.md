# Design

## Context

见 [proposal.md](proposal.md)。现有 Go 单服务在控制域提供浏览器 Cookie API 与 CLI Bearer REST API；`docs/control-api.md` 明确 MCP 尚无端点。CLI 在用户机器构建，校验静态清单，按文件上传到私有存储，再由服务端原子发布。CLI 的 `data status/reconcile/plan/apply/verify` 操作通过受限版本化清单管理每应用的表；应用数据存放在与控制库分离的 PostgreSQL 数据库，各应用使用隔离 schema。默认静态限制为单文件 10 MB、部署 50 MB；普通 JSON 请求限制为 1 MB。`apps/server/migrations/migrate.go` 已有带校验和的版本跟踪，下一项迁移可从 009 增量添加。根域由 Cloudflare Worker 按路径转发，新增入口必须同步路由和运维配置。

## Goals / Non-Goals

**Goals:**

- 一个可由 Codex、豆包等兼容客户端发现的远程 MCP 入口，服务端按同一所有者权限执行业务操作。
- 授权与 CLI 设备凭证隔离，并给只读查询、发布写入与应用数据表变更分别授予权限。
- 完全通过 MCP 工具传输有界静态产物；断线后可查询进度、幂等重试。
- 通过 MCP 完成现有版本化应用表管理流程，并将数据变更与静态发布的结果分别报告。
- 保持既有 REST/CLI 发布行为和地址；上线前在真实客户端与候选服务上验收。

**Non-Goals:**

- 服务端读取 Agent 本地路径、执行构建脚本、运行后端，或把项目源码作为发布产物。
- 首版的应用删除、访问密钥重置、旧版本回滚或完整控制台设置。CLI 对这些能力的既有支持不受影响。
- MCP 创建任意 PostgreSQL 数据库、执行任意 SQL、直连数据库或向 Agent 提供数据库管理员凭证；应用数据数据库仍由运维人员配置。
- 让远程 Agent 无需提供产物就能从其所在机器自动构建；Agent 必须有本地构建/文件读取能力，或由用户提供已经构建的静态文件。

## Decisions

### 1. 独立协议入口与服务端业务复用

在控制域提供 `/mcp`，由成熟的 MCP Go SDK 处理协议解析、版本协商、工具描述和标准错误；实现时选定并锁定支持目标客户端的 SDK 版本。工具适配层调用从现有 REST 处理器抽出的所有者应用、部署、上传和应用数据业务方法，避免从服务器内部发 HTTP 请求或复制校验。首版工具为 `list_apps`、`create_app`、`prepare_deployment`、`upload_file_chunk`、`complete_file`、`get_deployment`、`publish_deployment`、`data_status`、`data_reconcile`、`data_plan`、`data_apply`、`data_verify`。OAuth 是连接前的登录流程，不作为返回令牌的 MCP 工具。优先使用无服务端会话的请求处理，以适应多实例 Cloud Run；对旧客户端仅开启 SDK 明确支持并实际验收的协议版本。

备选方案是把现有 REST 路径改名为 MCP，或由工具自我请求 REST。前者不符合 MCP 协议；后者引入内部凭证透传和双层错误语义。

### 2. 单独的 MCP OAuth 授权边界

在同一控制域提供 MCP 受保护资源元数据与授权服务器元数据，以及授权、令牌、撤销和兼容客户端注册入口。浏览器沿用现有 GitHub/开发模式的所有者会话做身份确认，再显示客户端、`mcp:read`/`mcp:deploy`/`mcp:data` 权限和同意动作。授权码一次性、短时，强制 PKCE S256、精确回调地址和客户端绑定。优先支持客户端 ID 元数据文档，并为需要动态注册的客户端提供受限公有客户端注册；注册、回调与元数据 URL 做 SSRF 和重定向校验。访问令牌为独立随机值，仅存摘要及所有者、客户端、资源、权限、到期/撤销状态；不被 REST `owner()` 接受。MCP 认证失败在 HTTP 层返回标准 Bearer challenge，业务错误才进入 MCP 工具结果。连接可在控制台撤销；CLI 设备凭证列表与 MCP 连接列表分开。

备选方案是直接接受 CLI 设备令牌或浏览器 Cookie。它们缺少 MCP 客户端、资源和权限绑定，也不支持标准远程发现，故不采用。

### 3. 分块对象暂存与最终校验

`prepare_deployment` 复用现有清单、额度、请求标识和 `baseVersion` 校验，返回部署 ID 与固定分块上限（建议 256 KiB 原始数据）。Agent 把构建产物编码为 base64 分块，调用 `upload_file_chunk`，携带文件索引、偏移、长度和分块摘要。服务端限制 JSON 请求大小，校验连续偏移与同偏移幂等，分块放在私有对象存储的暂存命名空间，数据库仅记录元数据。`complete_file` 从暂存对象顺序流式合成文件，按原清单校验总长度和 SHA-256，然后走现有文件完成/发布状态逻辑。上传中断可从 `get_deployment` 的分块进度继续；过期暂存块按既有清理周期删除。写入对象与数据库无法原子提交时，通过幂等键和孤儿块清理恢复。暂存对象不对访客开放，也不能作为已上传文件发布。

备选方案是单次 base64 上传完整文件；默认 10 MB 文件会超过现有 JSON 限制且部分 Agent 工具参数有限。预签名直传虽可减少 MCP 调用，但要求 Agent 额外 HTTP 上传能力，不能满足首版纯 MCP 连接目标。

### 4. 发布结果与权限一致性

工具响应使用稳定的机器可读字段：应用 ID/URL、部署 ID、状态、已上传文件或分块进度、错误码与可重试说明。只读工具需 `mcp:read`，创建、上传和发布需 `mcp:deploy`，应用数据管理需 `mcp:data`；每次操作重新校验所有者、应用状态、发布暂停与令牌撤销。新应用创建沿用稳定 `requestId`；首版不经 MCP 返回初始访问密钥，应用访问设置仍由现有所有者控制台完成。发布成功只在已有原子发布事务确认后返回。跨服务测试覆盖同标识重试、同偏移冲突、过期授权、跨所有者和并发发布。

备选方案是以 MCP 会话保存发布进度；Cloud Run 重启或实例切换会丢失状态，因此使用已有数据库和私有对象存储。

### 5. 应用数据使用现有版本化清单

`data_status` 读取应用的数据就绪状态和已应用版本；`data_reconcile` 重试应用数据开通；`data_plan` 接收与 `cellapp.data.json` 相同的受限表、列、索引和权限结构并返回操作、摘要及 `requiresDestructive`；`data_apply` 接收相同清单和已审阅计划的摘要，重新计划并核对摘要一致后调用现有应用服务；`data_verify` 执行现有数据 API 探针。创建应用时仍由现有服务开通该应用 schema，MCP 不处理数据库 DSN 或 DDL 文本。数据管理只操作目标应用，默认未授权的表操作继续拒绝。破坏性计划须同时提供显式 `allowDestructive`，并沿用服务端现有版本冲突、事务回滚和幂等语义。表变更成功与静态发布成功分别返回，不互相替代。

备选方案是让 MCP 执行 Agent 生成的 SQL，或为每个应用创建物理数据库。前者突破现有清单与权限边界，后者改变运维与隔离架构，均不采用。

## Risks / Trade-offs

- [Agent 工具调用存在参数与次数限制，50 MB 产物需多次分块] → 公开分块上限和部署限制，在 Codex、豆包真实客户端验证；超出客户端能力时明确报告，不宣称发布成功。
- [OAuth 客户端支持的注册及协议版本可能不同] → 同时提供标准发现和受限注册，在候选环境记录两类客户端的授权与工具调用；将实际支持版本写入文档。
- [分块暂存造成额外存储与清理压力] → 暂存计入部署额度，设置上传 TTL、请求限速和孤儿块回收；失败不改变当前版本。
- [MCP/ OAuth 新路径被 Pages 或 Worker 错误路由] → 先更新候选路由与路径测试，再做授权和发布验收，未知路径固定返回失败。
- [发布与清理并发、撤销中途发生] → 所有写入在业务边界重新鉴权，完成文件和发布检查部署状态；事务/锁保持原有版本竞争语义。
- [Agent 误把建表当成任意数据库管理，或在未审阅计划时删除数据] → 工具只接受现有版本化清单，独立 `mcp:data` 授权；破坏性操作需要计划摘要匹配和显式允许，结果与前端发布分开报告。

## Migration Plan

1. 在既有版本跟踪迁移器上增加 009，创建 MCP 授权码、客户端/同意、令牌摘要与分块元数据表；不改写已执行迁移。新服务先部署到隔离候选环境。
2. 为候选控制域 Worker 增加 `/mcp` 与所需 `/.well-known/*`、OAuth 路径转发，更新 Go 路由、路径清单和运维说明。保持 CLI/REST 路径可用。
3. 用隔离账号、控制库、应用数据数据库和私有存储完成协议、OAuth、分块、表变更、权限、并发及真实 Codex/豆包连接验收，确认浏览器授权、发布 URL 与访问边界。
4. 候选通过后按项目发布顺序上线服务与路由，再发布连接文档；观察错误率、暂存清理和授权失败。回滚时先停止新 MCP 路由并回退服务，保留向后兼容的 009 表与既有应用发布；已发 MCP 令牌不可被旧服务或 CLI 接受。
