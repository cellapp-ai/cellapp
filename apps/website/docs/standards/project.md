# 项目规范

适用范围：Cellapp 产品官网。基线日期：2026-09-28。规则含义见 [规范入口](./README.md)。

## 1. 项目定位与范围

官网面向了解和试用 Cellapp 的访客，介绍静态前端从构建目录到 HTTPS 分享链接的工作流。当前页面包括首页、部署引导、价格、使用文档、博客列表及三篇文章详情；部署页可复制 Agent 指令，`/deploy/AGENTS.md` 提供静态 Markdown 指引。

当前官网使用本地内容数据和构建时静态渲染，没有后端、账号体系、CMS、结账、订阅创建或评论服务。价格为明确标注的预览；选择套餐打开文档并传递套餐和计费周期，不代表成交。导航中的 Dashboard 链接指向同一根域名的 `/dashboard`，由边缘路径路由转发至独立控制服务，不属于官网静态导出页面。

必须遵守以下边界：

- 页面上的操作必须与实际能力一致；演示发布流程和草案价格必须保留相应说明。面向用户的部署引导只要求 Agent 处理客户端准备和发布、用户在浏览器授权。
- 安装方式、CLI 参数、API、商业条款不得凭空补全。未验证的契约应引导读者查阅产品来源，并记录待确认项。
- 新增支付、用户数据、服务端能力、远程内容或部署方式时，先定义需求、数据与运行边界，再实施。
- 现有网站界面为英文，工程规范为中文；新增页面延续当前语言，语言策略变化应单独说明。

## 2. 技术与运行基线

| 领域 | 当前选择 | 协作要求 |
| --- | --- | --- |
| 界面 | React 18、TypeScript、Vite | 以现有客户端入口和静态渲染方式为基础 |
| 样式 | Tailwind CSS 3.4、项目 CSS、shadcn/ui / Radix 基础组件 | 优先沿用现有视觉变量和交互语义 |
| 内容 | `src/content.ts` 中的类型化数据 | 套餐、文档章节、文章避免跨文件重复定义 |
| 构建 | Vite、Parcel、HTML-inline、React 服务端渲染 | 正式交付使用完整 `build` 流程 |
| 部署 | Cloudflare Pages Direct Upload，项目 `cellapp-website`，自定义域 `cellapp.ai` | 发布完整 `dist/`；Git 推送不会自动发布 |
| 验证 | TypeScript、Oxlint、Playwright、axe | 工具覆盖与人工验收分别说明 |
| 依赖 | 根目录 `package.json`、`pnpm-lock.yaml` | 统一使用 pnpm 管理依赖，保持锁文件同步 |

版本以仓库清单与锁文件为准，不在规范中追随外部最新版本。当前清单声明 `pnpm@10.34.5`；本规范没有新增 Node 版本约束。依赖升级需单独验证构建和浏览器行为。

## 3. 目录与文件职责

| 路径 | 职责 | 修改约定 |
| --- | --- | --- |
| `src/main.tsx` | CSS 载入、路由解析、metadata、挂载 / hydration | 改动时同时验证 HTTP 与本地文件模式 |
| `src/App.tsx` | 共享站点框架、页面与交互 | 新增复杂页面优先拆分模块 |
| `src/content.ts` | 内容类型、数据、路由列表、页面 metadata | 内容与路由保持一致 |
| `src/components/ui/` | 可复用基础组件 | 不放套餐、文章等业务内容 |
| `src/hooks/`、`src/lib/` | 共享 hook 和工具 | 有复用需求时再抽象 |
| `src/index.css` | Tailwind 层及基础变量 | 关注与官网语义变量的兼容性 |
| `src/site.css`、`src/refinements.css` | 官网视觉与已有修正 | 修改前检查最终覆盖结果 |
| `src/fonts.css` | 构建脚本生成的字体内嵌样式 | 不手工维护，当前被 Git 忽略 |
| `public/`、`src/logo.ts` | 原始资产与内嵌 logo 数据 | Logo 更新时同步两种表示 |
| `scripts/` | 字体生成、打包、静态导出、预览及验证 | 构建不得顺带安装依赖 |
| `docs/standards/` | 长期协作规范 | 随行为和工具变化维护 |
| `openspec/` | 需求和变更记录 | 使用 OpenSpec 流程管理生命周期 |
| `.build/` | 中间构建结果 | 忽略并允许重新生成 |
| `dist/` | 完整静态交付物 | 通过构建生成，不手工修复页面 |
| `test-results/` | 截图、验证报告 | 作为验收证据，不作为源码 |

当前 `src/App.css` 未从入口导入，`src/assets/` 中存在模板资产；不得因为文件存在就把它当作生效设计基线。清理须在独立变更中确认引用和影响。

## 4. 开发与构建流程

在仓库根目录执行：

```sh
pnpm install --frozen-lockfile --registry=https://registry.npmjs.org
pnpm run dev -- --host 127.0.0.1
```

`predev` 自动生成内嵌字体。正式构建：

```sh
pnpm run build
pnpm run preview
```

预览默认地址为 `http://127.0.0.1:4181`，可用 `PORT` 调整。构建过程如下：

```text
Source + local fonts
        |
        v
Embed fonts --> Typecheck --> Vite + Parcel
                                   |
                                   v
                             Inline template
                                   |
                                   v
                     Static render for each route
                                   |
                                   v
                       dist/ + dist/bundle.html
```

`build:client` 只生成 Vite 中间结果，不能替代完整站点构建。构建脚本当前没有清理所有旧 `dist/` 文件；删除或改名路由后必须检查交付目录是否残留旧入口，不能仅看新页面生成成功。

## 5. 路由与静态交付契约

当前支持：`/`、`/deploy/`、`/pricing/`、`/docs/`、`/blog/` 和由文章 slug 生成的 `/blog/<slug>/`；另提供 `/deploy/AGENTS.md` 静态文件。

- 每个支持的 HTTP 路由必须生成独立完整 HTML；正文不能依赖客户端脚本才出现。
- 支持路径使用末尾 `/`。新增页面要同步页面解析、`routePaths`、metadata 和浏览器验证。
- 页面直接访问和刷新必须成功，不依赖开发服务器的 SPA 回退。
- 发布时交付整个 `dist/` 目录，不能只上传根 `index.html`。
- `dist/bundle.html` 是单文件审阅版本；本地打开时通过 `?page=` 导航。内部链接变更必须保留这个能力。
- 内嵌脚本、样式、字体和 Logo 必须在交付版本中可用；不得意外引入运行时外部字体请求。
- 新增或调整错误页面时，区分 HTTP 404 与客户端显示的 404。当前本地静态服务器对缺失文件返回简单 404，App 有独立兜底视图；尚未导出定制 `404.html`。

## 6. 内容维护

新增文章时在 `articles` 中填写唯一稳定 slug、类别、ISO 日期、阅读时长、标题、摘要和完整正文。路由列表由文章数据派生，但当前测试路由列表是手写的，必须同步更新。已分享的 slug 应保持稳定；确需改名时说明旧链接处理方式。

新增文档章节时维护唯一 `id`、导航标题、正文标题、介绍和步骤。锚点必须对应真实章节，命令复制内容必须与显示内容相同。

价格数据中的 `yearly` 当前表示“按年付费时的月均价”，年总价为 `yearly * 12`。修改价格必须检查月付、月均价、年总价、节省比例和传递参数；不得把年总价写入 `yearly` 而保留现有计算。

公开发布前按 [RELEASE_REVIEW.md](../../RELEASE_REVIEW.md) 确认商业信息、外部产品目的地、安装与 API 资料、文章内容和品牌资产。预览验收完成不等同于这些内容已经获得公开发布确认。

## 7. 验证与验收

| 变更类型 | 必要验证 |
| --- | --- |
| 仅规范 / 说明文档 | 路径和链接可解析，命令与源码一致，明确现状与待改进项 |
| 源码、内容、资源、构建或配置 | `pnpm run lint`、`pnpm run build`，查看并处理与变更有关的告警 |
| 页面、链接、交互、路由、构建交付改变 | 在正式 `dist/` 预览上执行 `pnpm test`，并人工检查受影响页面 |
| 删除或改名页面 | 加查交付目录残留和旧 URL 行为 |

浏览器验证需先启动预览；首次使用可执行 `pnpm exec playwright install chromium`。`TARGET_URL` 可指定被测站点，`PW_ARTIFACT_DIR` 可指定报告目录。当前脚本以有界面 Chromium 运行，需要可用的图形环境。

当前脚本覆盖七个路由的直达与刷新、metadata、导航状态、320 / 390 / 768 / 1440 px 防溢出、axe 检查、计费切换和套餐传递、精确复制、文档锚点状态、移动菜单、键盘焦点、减少动态效果、无 JavaScript 阅读与本地文件导航。截图和报告保存在 `test-results/`。

这些检查不等同于跨浏览器兼容性、所有交互状态或完整无障碍认证。新增页面须扩充覆盖；关键视觉修改须人工检查桌面与移动端。未经执行的检查写“未执行”，失败写明原因，不能引用旧报告当作本次结果。

## 8. 变更与交付

- 小型内容或说明修改保持范围明确；涉及产品行为、信息架构、路由或交付机制时，使用 OpenSpec 表达需求、设计、任务与验收。
- 新 OpenSpec 变更使用 CLI 创建；已有变更的更新、规范同步和归档遵循对应流程，不能手工标记完成来替代验收。
- 不覆盖其他未完成工作，不顺带格式化全仓库或升级无关依赖。
- 建议分支使用 `codex/<简短主题>`；提交和评审说明写清实际结果、影响范围、验证及已知限制。当前未配置强制提交格式。
- 规范例外必须在变更说明中记录原因、影响和后续处理方式；持续采用的例外应更新本规范。

交付检查清单：

- [ ] 需求、实现、文案和操作结果一致。
- [ ] 受影响路由、metadata、静态输出和本地文件模式已检查。
- [ ] 适用的类型、Lint、构建和浏览器检查完成，限制如实记录。
- [ ] 内容来源与草案标识正确，发布待确认项已更新。
- [ ] 文档、规范和需求记录同步，未混入无关改动。

## 9. 已知维护缺口

当前尚未归档已有 OpenSpec 变更；没有正式能力规范；类型检查不是全仓库覆盖；没有统一格式化配置或仓库内 CI 流水线；浏览器测试路由列表没有从内容数据派生；静态导出没有完整旧产物清理。本次将这些列为维护事项，不改变相应实现。
